Backup & Restore

Two ways to back this install up: automated scheduled snapshots written to a local directory (configured below), or an on-demand encrypted bundle you download by hand (further down). Most installs use both — the automated cadence for routine recovery, a hand-exported bundle before a risky change.

Automated backup

A supervised in-app sweeper writes a verified, encrypted snapshot on the cadence you pick. You can also trigger a run any time from the CLI: email-triage backup now (inside the container). Snapshots land in the output directory below; a host-side job relocates them to off-box / SMB storage — that part lives outside this app.

{{ csrf_input(request) }}
Encryption{{ m.help("How each backup is sealed. Master key: sealed with this install's master key — restore needs the master-key export. Public key (write-only): sealed to an off-box X25519 public key — the container can't read its own backups; restore needs the off-box private key.") }} {% set x25519_help %}

What it is. An X25519 public key is the shareable “lock” half of a modern elliptic-curve keypair (Curve25519). Anyone can use it to encrypt to you; only the matching private key — which you keep off this server — can decrypt. It’s a short PEM block beginning -----BEGIN PUBLIC KEY-----. Storing the public half here is safe: it grants no ability to read backups.

Generate it OFF this box (your own workstation), then paste only the public block into the field above:

# Windows / macOS / Linux — the built-in tool (no openssl needed):
python -m email_triage backup gen-keypair
#   -> prints a PUBLIC KEY block  (paste it above)
#   -> prints a PRIVATE KEY block (store in your password manager, NEVER the server)

# macOS / Linux alternative, if you prefer openssl:
openssl genpkey -algorithm X25519 -out backup-private.pem
openssl pkey -in backup-private.pem -pubout -out backup-public.pem

Pitfalls: paste the PUBLIC key, never the private one (a -----BEGIN PRIVATE KEY----- block is the wrong half). Don’t use age-keygen — its age1… format isn’t PEM and won’t load here. Lose the private key and public-key-sealed backups are permanently unrecoverable — custody is entirely on you.

On-demand encrypted bundle

Download an encrypted bundle of this install's state by hand — e.g. right before a risky upgrade. Independent of the automated cadence above.

Bundle = entire install. The full bundle contains every credential, audit row, and message-state row this install holds. Anyone with the bundle file and the passphrase has full access. Pick a strong passphrase (16+ random characters) and store the bundle apart from any other auth material.

Full bundle

Contains the database, the YAML config, optional TLS certs, and optionally the master key. Without the master key, the bundle's encrypted credential rows are unreadable -- which is the point if you also export a separate master key only bundle below.

{{ csrf_input(request) }}

Minimum 12 characters; 16+ random chars recommended. Store in a password manager. Forgotten passphrase = data loss.

Master key only

Tiny file (under one kilobyte) with just the encryption key for the credentials inside a full bundle. Store this somewhere different from the full bundle: different password manager entry, different cloud, different USB drive. Recovery requires both files plus both passphrases.

Use a different passphrase from the full bundle above. Same-passphrase defeats the split-storage point.

Restoring a bundle

Restore is CLI-only. On the target host, with the service stopped: 

email-triage restore <bundle>
# Auto-detects bundle type (full vs key-only).
# Prompts for the passphrase.
# Extracts to side-by-side .restore files.
# Print the swap-in instructions; operator runs them manually.

Don't drop a bundle into a running install. The CLI route forces a deliberate stop / restore / start dance.
